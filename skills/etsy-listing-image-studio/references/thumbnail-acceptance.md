# Brief-bound thumbnail acceptance

Read before planning, generation, QA or completion claims. These checks supplement the existing skill; publication still requires separate approval.

## Prerequisites

Lock the approved count N, product ID, design revision, brief revision, format, requested native/output targets and minimum acceptable native dimensions, workflow and owner-review requirement. Preserve N until the owner approves a change; there is no global 20-image default. Record exact source-asset IDs, paths and SHA-256 hashes for product, artwork, exact printed text and original approved logo. Missing inputs block dependent rows, not unrelated work. Never invent dimension, material, interior, packaging or fulfillment facts; preserve unknowns as TBC.

Use the phase/dependency rules in [handoff-intake.md](handoff-intake.md). A full N-row plan and a one-image fidelity pilot have different intake requirements. Record total planned rows separately from authorized active rows; full-set completeness is not a prerequisite for a self-contained authorized pilot. SKU-matched owner confirmations can establish facts within their stated scope without a second supplier approval; retain their provenance. Production permission, copy status and final acceptance remain separate.

Maintain one authoritative N-row plan. When N=20, require exactly one 20-row plan, updated in place by revision. Every row contains: row ID, role, buyer question, sender, recipient, occasion, exact approved overlay (or explicitly approved none), product view, evidence requirements and status. Unsupported context is TBC/not applicable until approved. Distinct buyer coverage is required; changes only to backgrounds, people or props do not make distinct roles. Do not invent missing roles or overlay copy.

Here, authorized upstream copy can be owner-approved, explicitly draft-authorized, or locked `AGENT_IMPLEMENTATION` within a delegated brief. Record that precise status; do not convert it into owner approval or re-ask word-by-word. Material role/claim changes beyond delegation remain gated. Technical PASS plus current production/private-use authority needs no new per-file approval unless a specific human requirement applies. Log `NOT_REQUIRED` with its basis rather than inventing an acceptance event.

Link every row, candidate, QA record and approval to product/design/brief revisions and source hashes. Source, design, text, brief or output changes invalidate affected QA and approval; count/coverage changes also invalidate set-level acceptance. Recheck affected rows before reuse.

## Owner square-thumbnail format gate

For this owner's Etsy thumbnail briefs, default to 1:1 square and request a native 2000 x 2000 pixels, or a higher supported square target. The owner's explicit update on 2026-10-27 accepts native 1245 x 1245 or larger, including 1254 x 1254. Thus 2000 x 2000 is the preferred request and 1245 on both axes is the default acceptance minimum. Record those two values and the actual decoded native dimensions separately. A file below the preferred request but at or above the minimum can pass size QA; disclose the actual size without calling it native 2K. A file below the minimum remains blocked until recovery or an explicit owner-approved brief revision. This is an owner-specific default, not a claim that Etsy universally mandates square. An explicit owner-approved hard aspect/size minimum controls the affected brief; non-thumbnail outputs retain their approved formats. Do not rewrite earlier size findings made under a different brief; record the later rule and re-evaluation separately, without inferring full-file acceptance.

Compose and generate natively for the locked square frame. Do not silently crop, stretch or pad previous landscape images into compliance. Keep the product, exact overlay and genuine logo comfortably within the frame, with safe margins checked visually; do not invent a fixed platform crop guarantee. Where a brief requires full generation/no cut-and-paste, retain that workflow. A format correction authorizes no compositing or workflow switch; if fidelity cannot be achieved under that workflow, use the existing recovery rules.

Decode each actual native candidate and final delivered file. For the default square brief, require width == height, width >= 1245 and height >= 1245, unless the owner explicitly locks a different native acceptance minimum. Record measured values and pass/fail per file; filenames, prompt requests and provider labels do not prove dimensions. Native 1245 x 1245, 1254 x 1254, 1448 x 1448 and 2000 x 2000 all pass this default size gate; 1244 x 1244 fails the minimum and 2000 x 1500 fails square. Upscaling does not repair a native-minimum failure. Square/size compliance alone never means accepted or publication-ready: all existing fidelity, logo, evidence, coverage, count, visual QA and required owner-review gates still apply.

## Batch camera angles and independent fidelity gates

Before generation, inspect the actual original pixels at full size, not only filenames, descriptions or earlier generated candidates. Record the visible exact artwork, flower/cross/logo details, printed text and placement, verified material appearance, geometry and proportions against source IDs/hashes. Unknown material or unseen construction remains TBC; never use a new angle to invent a back, spine, thickness, binding, interior or finish.

Add planned camera angle, source support and separate angle-QA/fidelity-QA statuses to each row's product view. Plan the batch together to avoid unnecessary repetition: front, gentle left/right oblique, overhead and held views are options only when original references support them. Use natural, readable front-facing views for technical details and personalization when useful. Do not force angle quotas or novelty at the expense of legibility, truth or product fidelity. Angle variety supplements distinct buyer coverage; it does not replace the requested N-row coverage or permit additional unsupported views.

Lock exact artwork details, text placement, material appearance and natural product proportions across all angles. Ordinary perspective may change apparent shape, but must not stretch/reshape the product or alter its design. Inspect returned files against the original pixels for both camera/composition quality and product/artwork/text fidelity. Record these as independent pass/fail gates. A visually pleasing angle cannot compensate for changed flowers, cross, logo, typography, print location, material or proportions; either failed gate prevents acceptance. Do not claim exact fidelity merely because the overall scene looks similar.

On redraw/distortion, stop the batch before repeating the method. Within the existing initial-plus-two-corrective-attempt maximum, strengthen original-reference conditioning only where the approved generator supports it; log the changed reference setting/prompt emphasis and inspect each result before continuing. Do not invent a reference-strength setting or repeat unchanged failing generation. Persistent redraw, unavailable conditioning or required workflow changes stop dependent rows: report the exact changed details, attempts and limitation. Whole-image generation does not guarantee original artwork pixels. Never silently switch to compositing/cut-and-paste or claim fidelity that inspection cannot establish; each brief's explicit one-pass constraint remains binding.

For an oblique mat, read [mat-floor-plane-profile.md](mat-floor-plane-profile.md): floor-plane coherence and original-design fidelity are separate checks. Correct foreshortening is not a physical-ratio failure; do not force a front-facing product into every camera angle. Full-view corner requirements, genuine occlusion and frame crop must be recorded separately.

Owner approval of one candidate's aesthetic applies to that candidate and scope only; it is not blanket permission to change artwork or designs in later products. Preserve current original source assets and their locked hashes until explicit approval to replace them with an identified candidate. Candidate review alone does not promote a candidate into the source of truth. Keep task-specific candidate decisions in that task's brief, not as permanent gates on unrelated products.

## Production and bounded recovery

- Product identity, artwork and exact text fidelity outrank scenery and aesthetic polish. Each requested image must contain genuine original approved logo pixels or remain blocked. Missing/approximate generated marks never pass. A logo-awaiting draft is not a completed image.
- Preserve the original brand pixels. Composite only under an authorized workflow. Respect explicit one-pass requirements; if that workflow cannot preserve fidelity, stop and ask before switching workflows. Do not silently reinterpret generation approval as compositing approval.
- Supplier mockups and AI illustrations must be identified as illustrative, never as real customer UGC or real finished-product photography. Genuine customer evidence requires supplied, authorized media.
- Visually inspect the first returned candidate before scaling the method across the set. Misdrawn artwork, identity or exact text stops the batch immediately. Diagnose against the locked source; change the corrective approach before retrying. Do not repeat an unchanged failing method.
- Allow at most two corrective attempts per row after the initial attempt within the approved workflow, unless the brief has a lower limit. Stop earlier on repeated systematic distortion, missing evidence, missing logo or a required workflow change. Mark blocked, record attempts and request the smallest missing decision. Never silently reset the retry counter or keep spending attempts on the same defect.
- Queue exhausted-row/method/fidelity exceptions and finish independent authorized rows before a consolidated decision where feasible. An explicitly approved extra grant can extend only its named row/pool/purpose; a proposed pool is not permission, and unused allowances are not freely transferable. Preserve all older attempts across versions and handoffs.
- Preserve native returned files and dimensions. Record native and derived resolution separately, with transformation provenance. Upscaling adds no original detail; disclose it and never use it to silently satisfy a native-resolution requirement.

## Separate ledger counts

Keep technical QA findings separate from an explicit owner exception. When the owner accepts identified files as shown despite disclosed visual or native-size defects, record the exact files/hashes, decision, exception and permitted use; the owner-accepted count may advance within that scope. Preserve failed/HOLD checks and source assets unchanged. Do not infer such an exception from "continue", rename it technical PASS, certify original logo pixels or physical accuracy, or inherit it in future briefs. Apply the existing thumbnail-before-video rule using that explicit scope; publication remains separate.

If the human expressly authorizes a bounded policy for named later files, per-file use can instead be delegated within that exact policy. Record the direct human evidence/context, SKU/design/brief, roles/count, permitted destination, method/attempt/native limits, covered disclosed defects and exclusions. Inspect every actual returned file and complete any required independent review/judge, then bind its exact SHA and each finding to the policy. Label `USE_AUTHORIZED_SCOPED_POLICY`, retain technical REVISE/HOLD, and never claim the human saw future files. A contact-sheet approval of existing files is not this delegation. “Continue”, silence, initial-generation permission or one accepted pilot does not establish it; unknown or stricter human gates remain pending unless explicitly revised. A use policy alone does not override systematic-failure stops or authorize more attempts/compositing. New wrong product/capacity/quantity/text, unsupported factual claims or other material uncovered defects hold the affected file. Changed bytes require fresh QA/policy binding; never inherit a prior exact-file acceptance or carry a policy into another brief.

Track separately: planned rows; attempted generation calls; returned candidate files; visually verified files; dimension-compliant files; accepted files; delivered files; publication-ready files. Attach actual file paths, hashes, measured width/height/format, row IDs and revisions. Record failed/rejected candidates without counting them as accepted. A call can return several files; a row can have several attempts. Do not infer one count from another.

## Candidate comparisons and accurate QA

Inspect the decoded final native file, not a generating preview. Before declaring another worker’s QA wrong, reconcile delivered versus actually reviewed artifacts using [the candidate receipt](handoff-intake.md#what-an-upstream-agent-should-hand-over). Bind each observation to the exact filename, SHA-256, source version and reference being compared; if a previous observation was wrong, preserve the historical record and add a dated correction identifying the affected file and evidence. Compare the latest candidate with the best prior candidate on the same source and criteria; newer is not automatically better.

Record separately: (1) observable product identity, shape, text, personalization and factual errors; (2) visible artwork or typography differences and their practical impact; (3) visible brand-mark differences; (4) missing provenance or inability to prove original logo pixels; and (5) native format and size. An unverified original-pixel condition is a HOLD under the existing logo gate, not proof that all pixels differ or that a buyer will notice. Distinguish content-generation failures from download, attribution or connectivity failures. Do not describe skill gates as Etsy platform rules or as an owner statement unless independently sourced.

For a similar wrong-pilot handoff, the companion ShineOn Skill has a [dated pilot-04/05 case](../../shineon-graphic-design-workflow/references/observed-cases-2026-11.md) when available; it is historical evidence, not a new acceptance decision.

These classifications improve diagnosis and communication; they do not waive the existing original-logo-pixels gate, same-product fidelity, owner-defined scope, attempt limits, source protection or publication controls. Report a systematic failure once with actual file evidence and the smallest unresolved decision; do not reset attempts by changing filenames, chats or roles, or repeat an already resolved question.

## Per-image success checks

For each selected row, perform every check on the exact delivered file:

1. Open/decode the actual image file, read its dimensions/format and compute SHA-256. Confirm existence and readability. Compare selected hashes across the set. A prompt, planned row, placeholder, duplicate/renamed file or failed candidate is not a finished image. Unique hashes alone do not establish distinct visual coverage.
2. Inspect at full size against locked source assets: product geometry/identity, original artwork, every printed/overlay text line, spelling/punctuation, readable copy, genuine logo pixels, placement, truthful supported facts and distinct role. Log pass/fail and inspection evidence for each image; provider success is not visual QA.
3. Compare measured format/dimensions with the approved brief and required current platform specification. Keep visual and dimension results separate. Disclosure of a gap does not make it pass. Native-resolution requirements remain binding unless the owner approves a revised brief.
4. Obtain owner review when required, tied to exact output hash and current revisions. Pending, failed or invalidated review cannot count as accepted/publication-ready.
5. For ordinary acceptance, require visual, dimension, evidence, fidelity and any applicable owner-review checks to pass. An explicit exact-file exception or valid per-file binding under an expressly delegated bounded policy follows the Separate ledger counts rule above and advances only permitted use; preserve all failed/HOLD technical findings and source/publication gaps. Deliver those exact bytes and record the authority type honestly. Publication-ready additionally requires all approved publication checks; readiness does not authorize upload/publication.

## Set success and stops

Claim N complete only for the stated scope when the authoritative N rows each map to one distinct, use-authorized, delivered file: actual selected file count=N, unique SHA-256 count=N, complete distinct coverage, readable dimensions, per-image QA findings and current required approvals. Ordinary completion requires the checks to pass; exact-file exceptions or expressly authorized scoped-policy bindings use the Separate ledger counts rule and must be named in the completion claim, not relabeled technical PASS, individual human viewing or publication-ready. Reconcile ledger and files before claiming completion. Six eligible files for N=20 is 6/20 with 14 remaining, never 20 done.

For partial delivery, report every ledger count separately, identify remaining row IDs, gaps, blockers and next recovery action. Missing files, duplicate hashes/coverage, unreadable dimensions, missing genuine logo, unsupported facts, failed QA, dimension gaps or stale/pending required approval stop completion/readiness claims. Deliver useful partial results explicitly; do not reduce N without owner approval.

Example: a pastor brief can return 20 actual candidate files at 1448x1086. They may undergo visual review, but fail a higher approved dimension target and cannot be marked publication-ready. Report returned=20 separately from visually verified, dimension-compliant, accepted and delivered counts.

These are brief acceptance rules, not new Etsy policy claims. Preserve existing verification of current official guidance when relevant.

## Thumbnail-before-video gate

When the brief requests thumbnails followed by a product video, complete the required thumbnail set for that exact SKU and design revision before starting that SKU's video generation or rendering. For an authorized 20-image brief, all 20 distinct rows must map to the exact files that pass the existing per-image and set acceptance gates and have been delivered; a plan, prompts, a few scene images, or a previously rendered video do not satisfy the gate. Record accepted file hashes and QA status in the SKU task record before opening its video phase. Partial, blocked, failed or pending sets keep that SKU's video phase blocked. Independent work for other SKUs may continue. Build the video only from the matching accepted thumbnail assets, following the requested duration (15 seconds when specified), product theme, approved text and brand. A later source or thumbnail revision invalidates affected video checks. Any owner-approved exception must be recorded with its exact scope; it must never be inferred from a request to continue.
