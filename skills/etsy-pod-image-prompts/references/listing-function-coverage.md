# Listing-set functional coverage

Use this reference when planning or accepting a complete listing-image set. Derive required functions from the current product brief and its source documents; do not use image count, a role label, aesthetic approval or packaging success as a substitute for buyer-question coverage.

Neither source prescribes a fixed allocation of twenty images across categories.

The SOP's middle section headings reverse those two labels; resolve by meaning, not by copying the inconsistent number. Preserve a current owner-approved change if one is supplied.

The SOP's example sizes, processing days, custom fields and overlays are teaching examples, not current SKU facts. Later explicit editing-method authorization governs its own scope; reading this functional reference does not reinstate an earlier superseded method restriction or grant new editing authority.

## Required map for this journal brief

1. Search/hero clarity: make the product and the actual search/buyer intent clear. First-photo source eligibility remains a separate gate.
2. Personalization proof: identify what can change and show the actual permitted personalization without implying extra fields.
3. Product reality/interior/use proof: answer how the journal is a usable product. Distinguish a verified page-count statement, an illustrative use scene and actual interior evidence; one is not proof of the others.
4. Material and size confidence: show or state verified material, construction and physical size as required. Cover texture alone does not establish dimensions; artwork pixel dimensions are not the object's physical measurements.
5. Gifting: show a credible gift purpose or relationship moment without inventing included packaging or customer reactions.
6. Use context: demonstrate an accurate, relevant use such as ordinary writing or notes. A lined interior is not guided devotional content.
7. Emotional purchase reason: express the intended relationship or meaning while preserving the product's real offer.
8. Ordering/customization steps: explain the actual steps and inputs clearly. “Personalized with a name” or “only the name changes” establishes scope, not a complete ordering sequence.
9. Production/processing/trust information: supply truthful, sourced production or processing/policy information relevant to the buyer's remaining concern. Separate processing from delivery estimates. Do not invent turnaround, arrival dates, guarantees, ratings or reviews.

For a non-custom product, follow the current brief's documented replacement of personalization/order functions with relevant options, sizing, care or contents proof. Do not infer new fields from the SOP's generic examples. Offer/bundle imagery is optional and needs a real current offer.

## Build the acceptance map

Before generating, record one primary job per planned image. At review, map the actual final exports, not the plan or prompt. Retain these fields for each required function:

- Product/set ID and source brief/version
- Function ID, buyer question and required scope
- Final image ID, version and measured hash; primary or secondary role
- Actual visible evidence, including exact practical wording and what can genuinely be seen
- Product/claim source and date, with missing facts explicit
- Verdict: PASS, PARTIAL, MISSING or BLOCKED; reason and the smallest missing fact/asset/action

A file may support a secondary function only when the visible content genuinely answers that question; do not double-count decorative variations. Keep required coverage and the number of scene variants separate. A proposed twenty-image blueprint is a reviewable plan for that brief, not evidence that an existing set already complies or a fixed rule for every listing.

For requested supporting questions such as date options, delivery timing or what is included, map the exact question to the relevant personalization, product or trust function. Mark a current name-only offer accurately; do not add dates as an option. Do not silently declare a FAQ answered by unrelated scene copy.

## Separate acceptance gates

Report independently: file count and actual delivery; technical/visual quality; factual accuracy; functional coverage; owner acceptance of the exact version; production and publication readiness. All required functions must pass before claiming full functional completion. An unresolved mandatory function keeps that gate PARTIAL/BLOCKED even if twenty attractive files have been delivered.

Missing dimensions, interior sources or processing evidence do not authorize invented content. Preserve the delivered files and valid historical approvals; list gaps and a bounded correction proposal. A review/category question alone does not authorize new generation, reorder the current set or publish it. Correct the affected scope only after the applicable user instruction, then recheck changed files and the whole set's coverage map.
