# Decision ownership and fewer interruptions

“代答” means make routine production judgments within authority, never fabricate owner consent. The aim is to remove redundant questions, not hidden gates.

## Pre-question check: execute in this order

Before sending any question, identify a stable decision key such as `product/research-round/source-order` or `product/role/file-hash/fidelity-exception` and check the question ledger. Bind only relevant dependencies: a new image filename/revision does not reopen source order for the same research round. Exact output bytes do matter for a visual exception.

1. **Prior decision:** recover the latest applicable owner wording, current charter, source-order answer, plan/pilot acceptance, exact-file exception and extra-attempt grant. Match product, version, purpose and limits. A new turn, handoff or filename does not erase authority or attempt history.
2. **Readable sources:** inspect the named current record, source file or authorized UI. Do not ask the owner for data already present. A genuinely new conflicting value invalidates only the affected dependency.
3. **Delegated routine judgment:** if the owner delegated wording/layout/ordinary composition within a fixed mission, decide and record `AGENT_IMPLEMENTATION` plus its authority pointer. Upstream can lock this copy for Studio. Never falsely mark it `OWNER_APPROVED`; never use this path for an owner-controlled gate.
4. **Optional unknown:** omit an unsupported optional claim or keep it `TBC` internally, then continue. Do not put internal TBC into buyer copy or invent a substitute fact.
5. **Material missing decision only:** if a required identity, source conflict, method/cost change, exact-file failure exception, security interaction or explicit human acceptance remains unresolved, ask the smallest concrete question and record its dependency.

Operational target: **zero routine questions**. Start with zero questions if the charter is recoverable; otherwise combine the necessary intake into one bundle where possible. No automatic plan-approval or finish-approval round is added by this Skill. Final owner acceptance is requested only where the current task/rules actually require it. Genuine new safety or failed-QA gates may require later bounded questions; this is not an unsafe absolute question cap.

## Recover the execution charter once

Populate the existing record from current authority before work; the owner does not need to fill a form. Capture:

| Charter area | Required decision fields |
|---|---|
| Endpoint | Product/variant/artwork/brief revision; scope mode; exact completion condition; exclusions |
| Production | N roles, active rows, upstream copy status, materially locked direction, matching pilot and source hashes |
| Methods | Actual service/browser route; whole-image constraint; separately authorized logo/footer/inset exceptions with permitted region/purpose |
| Budgets | Provider currency/cost cap if any; per-role submission/correction ceilings; cumulative used/pending/uncertain calls; exact additional grants and remaining balance; separate video allowance |
| Reviews | Required QA; any specified reviewer/judge model and reasoning; named human gates and basis; exact-file versus final-set/video scope |
| Private mutations | Which product fields, uploads, selection/order, save/reopen and native video actions are covered; price/shipping/Push exclusions |
| Recovery and delivery | Current operator, pending operations/jobs, before snapshot, accessible delivery route and next safe action |

For every potential human gate use `NOT_REQUIRED` with the actual delegated/current-scope basis, `REQUIRED_PENDING` with its source, `SATISFIED` with exact evidence, or `INVALIDATED` with the changed dependency. Absence of a gate in a template is not proof it is unnecessary. Routine technical PASS inside authorized count/route/budget/private use can be `NOT_REQUIRED`; a known human requirement or failed-fidelity exception cannot.

The default image ceiling remains **initial + at most two targeted corrective attempts per row**, subject to any stricter brief and actual spending authority. It is not a fresh allowance on resume. Preserve old calls, uncertain submissions and extra grants. Stop earlier for systematic failure. Video uses its own current task allowance; this case's four video candidates are not a new default.

If several rows need additional attempts, finish independent eligible rows and propose **one pooled extra-budget decision** identifying affected rows, changed approach, incremental maximum calls/cost, distribution rules, expiration and stop condition. A pool exists only after explicit owner approval. Do not silently increase per-row limits, transfer unused grants between roles, spend on a new provider or treat unknown cost as zero. Reconcile uncertain charged submissions before calculating remaining budget.

## Intake without a questionnaire

Read current decisions and evidence first. Ask only the smallest set that affects the next work. A useful bundle might contain exact destination if truly unknown, source order if a new unanswered round, and one material direction decision. Do not ask for output count, price, market or logo when already specified or readable.

Separate a **recommendation** from a **permission request**. For a reversible implementation preference, state the assumption and continue when allowed. For missing required approval, silence is not consent. Offer a concrete proposed choice and consequence, not “what should I do?” If independent work remains, proceed while the question is pending.

For visual exceptions, finish all independent eligible roles and present a small, labeled batch with actual previews, role/revision, exact differences, native dimensions and hashes. One reply may cover that explicitly enumerated batch. Do not turn “continue” or acceptance of one pilot into approval for unseen files. Conversely, never ask again for the same accepted hashes.

### Explicit bounded batch policy

A human may explicitly delegate use decisions for named later files within a narrowly defined policy. This differs from accepting a contact sheet of already-existing hashes. Recover the direct reply and its question/context, product/design/brief, affected role IDs/count, permitted use, method and attempt limits, native requirements, disclosed defect categories and exclusions. The owner must actually authorize that later-file category judgment; the agent cannot create it to reduce questions. Ambiguous “all approved” without a clear referent is not enough; resolve the missing boundary once. Silence, “continue”, generation permission, or an accepted pilot is not batch exception authority.

After each actual file returns, preserve per-file technical QA and any required independent review/judge, exact SHA, actual defects and their mapping to the permitted categories. Record `USE_AUTHORIZED_SCOPED_POLICY` only when all limits hold; retain technical REVISE/HOLD, original sources and warning/disclosure requirements. Do not claim individual human viewing of future files or mark a failed human gate `NOT_REQUIRED`: the scoped gate is satisfied only by the actual policy plus its applicable per-file binding. New wrong wording, product/capacity/quantity, unsupported factual/policy claim or other material uncovered defect holds that dependent file; known false claims do not become eligible by disclosure.

A use policy is not extra generation/budget/method permission. Persistent systematic-failure stops still apply unless the owner expressly authorizes that bounded production continuation as well. Source/brief/policy changes invalidate affected bindings. New bytes require a fresh eligibility check under the still-current policy, not inheritance of the earlier file's acceptance. Do not carry the policy to another SKU or publication scope.

Use the same queue for exhausted retries and proposed method changes: add the exact failed output, remaining count, corrective option and incremental cost/limit. Do not interrupt after each row to repeat the same decision. Never lower N, substitute a role that fails its buyer question or restart an exhausted row while waiting. A truly immediate security interaction may require its own owner handoff; unrelated local work continues.

“Independent rows” does not mean continuing the same systematically failing generator method under new role numbers. A shared product/art/logo defect pauses the affected visual family until diagnosis changes a supported input/control/method within authority. Copy, authorized research, source checks, unaffected information cards or an already-verified independent method can continue; do not burn the remaining budget reproducing a known shared failure.

For money/business decisions, provide the completed scenario first: item price, buyer shipping, supplier cost/shipping, platform fees if known and estimated contribution. A cap such as shipping <=5.99 is a constraint, not permission to choose any unrelated profile or invent its actual charges. If the owner later skips shipping, close that action in this task.

## Decision ledger

Each material entry records decision ID, exact owner wording or trusted source pointer, date, product/variant, round/revision, action/purpose, limits and exclusions. For image exceptions add exact SHA-256. For delegated routine choices record `AGENT_IMPLEMENTATION`, rationale and applicable authority; never label them owner approvals.

Decisions remain valid while scope, product, version and relevant facts match. Revalidate only the changed dependency. Do not expire all permissions on a new turn or handoff, and do not carry them to another SKU or paid provider.

Question ledger fields: `decision_key`, `needed_for`, `source_checked`, `existing_answer`, `human_gate/basis`, `state` (`NOT_NEEDED`, `QUEUED`, `ASKED`, `RESOLVED`, `INVALIDATED`), `question_or_batch_id`, `answer_receipt`, `affected_rows/actions`, `next_safe_action`. A resolved key is reused on resume. A reopened key needs a stated new material change; do not ask the same source-order question again for the same round.

## Progress and stop behavior

Keep commentary meaningful and regular under the host's requirements. Explain one finding and next resolving action; do not narrate unchanged polls. Do not let a long tool wait prevent required communication; use the current tool's supported yields and permitted wait intervals.

When all independent work is done, leave a concrete checkpoint and pending question. Do not keep creating cosmetic audits or duplicate deliverables to appear busy. Goal tools, if available, follow their documented blocked/complete rules exactly; do not invent a new blocked threshold or claim completion to stop continuations. A user-requested resume begins the applicable fresh blocker audit. Do not create an automation or repeated wakeup without a user scheduling request.
