# ShineOn Graphic Design 專案流程

在適用的 ShineOn Graphic Design 專案，按 owner 的實際要求統籌多款產品、跨階段處理單款，或只完成指定階段。主線管理分工、依賴、共用資源、成果核對及總狀態；它不是額外的商品執行者，也不自動擴展至完整 listing。以繁體中文／廣東話報告；面向買家的文案依 brief 的語言。

## 1. 綁定本次範圍

先讀適用 root／project 規則、最新 owner 指示及本款目前有效紀錄；只有解決缺口或衝突才追讀歷史。核對 product ID、SKU／variant、原始素材及 revision，不能只靠標題或舊 tab。將實際授權的階段、目的地、數量、費用／次數上限、排除項及 human gate 記錄在現有 task record；未知寫 TBC，已有有效決定不重問。歷史作案例或證據，不承接其他產品、批次或一次性批准。

將請求辨為單階段、多款專案或單款跨階段，選相稱的簡短記錄與 QA。單階段完成只代表該階段達標；未在範圍內的依賴可標未驗，不自動啟動其他工作。實際改動高風險核心 workflow、schema、權限、production 或重大決定時，依當時適用規則及指定 evaluator／human gate 路由；不要因普通可逆設計工作自動套完整 LoopForge。

本 Skill 不授權 Send、Publish、Deploy、Schedule、Etsy push／sync、付款、廣告、修改正式 Skills／規則、安全或權限、處理憑證／私人敏感資料、覆蓋／刪除重要檔案，或擴 scope／成本。私人 APOD 寫入、上載及其他平台動作必須在當前 owner 有效授權及適用規則內；已有明確界限的批次授權可涵蓋其中各檔案及欄位，不必為已涵蓋的每個動作重問，也不能推定新授權。對依賴未獲批准動作的步驟，先備妥可審核的具體材料，再向 owner 提出最少必要決定；已授權的獨立工作繼續。不可由設計稿、繼續工作或本 Skill 推定批准。

## 2. 主線與產品任務

多款、跨階段、涉及共享 browser 或中斷續辦時，讀 [主線統籌與交接](references/coordination.md)。主線建立或沿用一份當前狀態，拆分各款及依賴，給每款同一時間一名具名 product owner、獨立目的地和版本；每個階段亦只有一名 artifact owner。可由同一人兼任，不能讓兩人同時改同一成果。視授權、成本及依賴選擇有限並行或順序；簡單任務可由主線一人處理，不因框架而啟動新 agent。只有在當前 runtime、owner 和適用規則允許委派時才派 agent，記錄真正啟動、交付及停止狀態。

主線用收到的來源、實際成果與回讀證據檢查 product ID／revision／hash／步驟及其未驗界線，不能只複述 worker 聲稱。保留每款阻塞和獨立可做項，按依賴更新總狀態；不以另一款進度、完成數或舊版審視補齊。HOLD／paused 按原狀保留，只有適用 owner 明確恢復後才從實際 checkpoint 續做。交接、共享 browser lease、衝突及清理按該 reference 執行。

## 3. 正確銜接既有專才

先確認 Skill 在當前環境存在，按名稱及本次階段讀取，不因提及而啟動 agent 或授權支出。每階段只有一個 production owner；保留原 task record 和完成證據：

- 買家、定位、送禮、來源、需要時的研究與文案：在該範圍內使用 etsy-coach-integrated 的相關方法。
- owner 明確要求選定實體產品的完整 private APOD listing build 或該流程跨階段續做：由 etsy-apod-product-workflow 擔任該款的既有 coordinator；本專案主線仍負責跨產品分派、資源與總狀態，接收其結果，不另行重跑或指揮重複階段。沿用其完整 build 的 mockup-first 依賴與現行適用合約；不因此替單獨設計／圖片階段增加 listing、影片、20 張圖或平台寫入。
- 同款縮圖／mockup 的製作與視覺 QA：使用 etsy-listing-image-studio 的對應 image phase；交回實檔、revision、hash、次數及 QA。
- 適用 project 規則或 owner 要求買家角度檢視時，按當前產品、版本、範圍和已授權成本使用 superpersona。模擬觀點不是實際買家或市場研究，也不代替技術 QA、owner acceptance。過去次數不是新批次配額。

把明確授權的單款完整 listing 交給 APOD coordinator 時，傳該款完整 charter 與同一份 record，不把 coordinator 限成單一 phase。Coordinator 再向 Coach、Studio 等 specialist 傳 phase-only；若本來只請 specialist 執行指定階段，亦只傳 phase-only。各階段完成後回原 coordinator／主線，不能在各入口之間遞迴 routing、重新 intake 或重做仍有效的成果。若既有 Skill 的一般預設與較近有效 project 規則或當次 owner 範圍不一致，保留較嚴格的適用門檻，不藉路由擴權；真正衝突只停受影響步驟並交 owner。

## 4. 產品設計與個人化

對在 scope 的產品，先說清 buyer、giver／recipient、occasion、情感、實際 SKU 與原創構圖；將姓名等變數融入送禮故事，對批次中相關款式比較實質差異。來源、可核實產品事實、設計判斷及未知分開；不複製參考構圖、不把換色／換名／通用經文當成實質差異，不聲稱市場需求、銷售或未證實工藝。

Project 規則適用時，每款最終產品須同時有實質差異及真正可編輯 personalization。按實際 SKU 支援及關係規劃姓名等字段，固定 illustration 與可變內容分開；示例姓名、PSD 文字 descriptor、seller-only layer 或 listing 寫上 personalized，均不能單獨證明 customer-editable field。只做概念／圖片階段時可交付明確標示的局部成果，但不能稱整款完成。

按目前 project／owner 指定的圖像路徑執行；適用本批規則時，原創圖像以 ChatGPT 網頁版生成，版本不限，不猜 backend，且不得把可變姓名烤死在圖片中。新批次依當時適用規則及明確指示，不把一次性 logo-only、額外生成或其他特例轉移。路徑不可用時停依賴步驟，不靜默改用本地、API 或其他服務。

## 5. 實作與證據

需評估 APOD、mockup 或印刷時，讀 [產品與證據檢查](references/product-evidence.md)。在實際獲授權的 APOD 正常 editable text／customer field 實作並核實；記錄實際 label、字體、位置、限制及來源，未知為 TBC。至少用兩組不同長度的 synthetic 輸入，對每組執行改值 → 預覽變化 → 保存 → 重開讀回；逐欄記可變性及 customer／seller 層級證據，不保證未測輸入。APOD 與 Etsy buyer-field mapping 分別驗證，私人保存不證明 Etsy mapping。

使用同 SKU 的真實模板／印區；最終 thumbnail／mockup 必須與同款、同 revision 的 personalized mockup 一致，逐張核對可讀性、裁切、產品形狀、來源、版本與 hash。畫面 QA、私人保存與重開、印刷 preflight、實物／supplier 確認及 production release 分開記錄。沒有適用印刷證據時保留 TBC／HOLD，不從像素或 metadata 推斷可印、白墨或物理 PPI。

## 6. 結束與續辦

每款交接列明實際完成階段、檔案或遠端身分、證據、revision、測試、阻塞、權限／下一步和唯一 owner；未做、失敗、模擬及不可驗分開。主線核實收件，更新各款狀態及整體依賴，並按需要驗證 browser 清理。最終回覆包含可用成果、剩餘條件和具體續辦；私人 QA、模擬買家審視、owner acceptance、實物驗收和正式發布各自獨立，不互相代替。
